# 고급 상세 검색 — 1단계 보고서 (현황 점검 · DB 설계안 · 화면 계획)

> **상태:** 승인 ①·② 완료(2026-10-22) · 화면 작업 완료(커밋 전) · **승인 ③ 대기** — 실제 화면 확인(7장)  
> **작성:** 2026-10-22 · 기준 커밋 `0e3325d` + PRD 0.7.2(결정 D1~D4)  
> **근거:** 저장소의 코드와 마이그레이션 파일을 읽어서 확인했다. 승인 ① 뒤 운영 DB를 읽기 전용으로 조회해 개수와 구조만 확인했다(5.3). 마이그레이션 초안은 운영 DB가 아닌 내 컴퓨터의 임시 Postgres에서만 시험했다(6.2).  
> **이 문서는 계획이다.** 이 문서만으로 코드·DB·Auth·Storage를 바꾸지 않는다.

## 0. 한눈에 보기

- 지금 앱에는 **검색 화면이 없다.** Search 탭과 Home의 `Search` 카드는 "Search is coming soon."만 띄운다(`js/app.js` 79~80행, `js/views/home.js` 122행).
- 8개 검색 축 중 지금 데이터가 있는 것은 **Music Parts, Date, Season(미사에 저장된 값)** 뿐이다. 작곡가 사전·시대·조성·장소 목록·실제 연주 기록을 담을 칸이 없다.
- 그래서 순서는 **DB에 칸 추가 → 검색 함수와 자동 테스트 → 연주 확인과 악보별 연주 이력 → 검색 화면**이다.
- DB 설계는 **추가만** 한다. 기존 테이블·칸을 지우거나 이름을 바꾸지 않고, Auth·Storage 정책·기존 RLS 정책은 바꾸지 않는다. 기존 미사 기록·악보·연결은 그대로 남는다.

**설계 문서와 다른 곳 (구현할 때 함께 정리):**

- 반복 미사 삭제 화면(`deletionGroups`)은 `performance_confirmations`가 있는 미사를 "연주 기록 있음 → 자동 삭제 안 함"으로 분류한다. D1 이후에는 **지난 날짜이고 곡이 연결된 미사**를 연주 기록이 있는 미사로 봐야 한다.
- 지난 미사에서 곡의 연결을 해제하면 D1 기준 연주 이력에서도 빠진다. 안 친 곡이면 연결 해제 대신 `Not played`를 쓰도록 안내가 필요하다.

## 2. DB 설계안 — 추가만 (승인 ②에서 적용)

**공통 원칙**
- 기존 테이블·칸·정책은 지우거나 이름을 바꾸지 않는다. Auth, Storage 버킷·정책은 건드리지 않는다.
- 새 개인 테이블은 기존과 같은 RLS(`user_id = auth.uid()`)와 `(id, user_id)` 복합 외래키를 쓴다. 다른 사용자의 행을 가리킬 수 없다.
- 새 함수와 뷰는 **호출한 사용자 권한으로 실행**(`security invoker`)해서 기존 RLS가 그대로 적용된다. `search_path = ''`.
- 마이그레이션 파일은 `supabase/migrations/`에 나누어 만들고, 각 파일 머리에 무엇을 추가하는지와 되돌리는 방법을 적는다.
- 운영 DB에 목업 데이터를 넣지 않는다. 기준 데이터는 사용자가 정한 값(시대 경계 C8)과 출처를 확인한 값만 넣는다.

### 2.1 실제 연주 (D1)

| 추가 | 내용 |
|---|---|
| `mass_music_entries.not_played_at` | `timestamptz`, 비어 있으면 표시 없음. 사용자가 `Not played`를 누르면 그 시각을 저장하고, 풀면 비운다 |
| `mass_music_entries.note` | 그 미사에서의 연주 메모(Notes View의 "연주 기록 메모"). 2.6 참고 |
| 뷰 `performed_entries` | 연주한 곡 한 줄 = 곡 연결 한 건. 조건: 미사가 `cancelled`가 아니고, `local_date` < 오늘(한국 시간), `not_played_at`이 비어 있음. 열: 연결 ID, 악보 ID, 미사 ID, 날짜·시간, 전례 시기, 전례일 ID, Music Part(역할 ID·표시 이름), 장소 ID·장소 이름 |

- **따로 "연주함"을 저장하지 않고 계산한다.** 날짜가 지나면 저절로 연주한 것으로 보이고, 미사 날짜를 고치거나 취소하면 결과도 바로 맞춰진다. 밤마다 도는 자동 작업이 필요 없다.
- 악보별 연주 횟수·연주 이력(SCORE-013)과 검색의 `Performances` 축이 이 뷰 하나를 같이 쓴다.
- `performance_confirmations` 테이블은 그대로 둔다(비어 있음, 삭제하지 않음).
- **기존 데이터 영향:** 이미 지난 미사에 연결된 곡은 적용 즉시 연주한 것으로 계산된다(D1 결정대로). 기존 행의 값은 바뀌지 않는다.

### 2.2 내 장소 목록 (D3)

| 추가 | 내용 |
|---|---|
| 테이블 `user_venues` | 장소 한 줄: `name`(1~100자, 입력한 그대로), `layout_id`(연결할 Music Parts 구성 하나, 구성을 지우면 비워짐), 생성·수정 시각. 같은 사용자 안에서 대소문자·앞뒤 공백만 다른 같은 이름은 하나만 허용 |
| `mass_events.venue_id` | 미사가 고른 장소. 장소를 지우면 비워짐. **기존 `venue_name`은 그대로 남김** |
| `mass_series.venue_id` | 반복 미사 설정이 고른 장소. 같은 방식 |

- 장소 검색과 장소별 횟수는 `venue_id` 기준이다. 화면의 장소 이름은 장소 목록의 이름을 쓰고, 연결이 없는 예전 미사는 `venue_name`을 그대로 쓴다.
- **기존 장소 이름 옮기기 `[승인 ① a — 이름이 정확히 같은 것끼리]`:** 추천은 사용자별로 지금 미사·반복 미사에 적힌 장소 이름을 앞뒤 공백만 정리해 **이름이 정확히 같은 것끼리** 장소 하나로 만들고 `venue_id`를 채우는 것이다. `venue_name` 값은 바꾸지 않는다. "명동성당"과 "명동 대성당"처럼 다른 이름은 자동으로 합치지 않는다. 이 작업은 기존 행에 `venue_id`를 채우므로 승인 ②에서 따로 확인받는다.
- 비슷한 이름을 사용자가 직접 합치는 기능은 이번 범위에 넣지 않는다(필요하면 다음 단계).

### 2.3 작곡가 사전

| 추가 | 내용 |
|---|---|
| 테이블 `composers` | 표시 이름(예: `J. S. Bach`), 전체 이름, 한국어 이름, 생년·몰년과 확실성, 국가/활동지, 검증 상태, 출처 URL, `created_by`(비어 있으면 운영자 기준 자료, 값이 있으면 그 사용자의 개인 기록) |
| 테이블 `composer_aliases` | 작곡가 ID, 별칭, 검색용 정규화 문자열(악센트·대소문자 제거), 언어 |
| `owned_scores.composer_id` | 악보와 작곡가 연결. 작곡가를 지우면 비워짐. **기존 `composer_name`은 그대로 남김** (사전에 없는 작곡가는 지금처럼 글자로) |

- 권한은 기존 `works`와 같다: 운영자 기준 자료와 본인 기록만 읽고, 본인 기록만 쓰기.
- **작곡가 30명(부록 B)은 이 마이그레이션에 넣지 않는다.** 출처로 생몰년·이름·국가를 확인한 목록을 따로 보여 드리고 승인받은 뒤 넣는다(PRD 8장 23번, COMP-001).
- 사전이 비어 있는 동안에도 작곡가 검색은 `composer_name` 글자 검색으로 동작한다.

### 2.4 음악사 시대

| 추가 | 내용 |
|---|---|
| 테이블 `musical_periods` (운영자 기준) | 5개 기본 시대와 `[start, end)` 연도: Renaissance `[1450, 1601)`, Baroque `[1601, 1751)`, Classical `[1751, 1801)`, Romantic `[1801, 1901)`, Modern `[1901, ∞)` — C4·C8 결정값 |
| `owned_scores.composition_year`, `composition_year_approx` | 작곡 연도(확정/추정) |
| `owned_scores.period_code` | 사용자가 직접 고른 시대(고르지 않으면 비어 있음) |

- 악보의 시대 판정 순서: ① 사용자가 고른 시대 ② 작곡 연도로 계산한 시대 ③ 작곡가 생몰년에서 나온 **잠정 시대**(작곡 연도와 같은 것으로 취급하지 않음, 화면에 "잠정"으로 표시). ③을 검색에 포함할지는 5장 b에서 정한다. `[승인 ① b — 포함하고 "잠정"으로 표시. 검색 조건에서 뺄 수도 있음]`
- 사용자가 만드는 세분화(20th Century 등, C4)는 이번 범위에 넣지 않는다. 기본 5개로 먼저 출시하고 다음 단계에서 `user_periods`로 추가한다.

### 2.8 검색 함수와 인덱스

**`search_scores(조건)`** — `Scores` 대상. 화면은 `supabase.rpc`로 부른다.

- 조건: 검색어(제목·임시 제목(파일명)·작곡가), 전례 시기, 전례일, 연도(단일·여러 개·범위), 월(연도 없이도), 날짜 범위, 작곡가(여러 명 OR), 시대(여러 개 OR), 조성, 장소(여러 곳 OR), Music Parts(여러 개 OR), 횟수 조건(`=`, `≥`, `≤`, 범위), 정렬, 페이지.
- **같은 기록 판정:** 전례 시기·전례일·날짜·장소·Music Parts는 `performed_entries`의 **같은 한 줄**에 모두 맞아야 한다. 그래서 `Lent + Postludium + 1회`는 사순 시기 미사에서 Postludium으로 정확히 1번 친 곡만 나온다(D2).
- **횟수:** 기본은 조건 안의 횟수(`Within Filters`). 추가 조건으로 전체 횟수(`All Time`)와 장소별 횟수(`By Location`)를 하나 더 걸 수 있어 "전체 5회 이상 AND 흑석동 0회"가 된다.
- **0회:** 내 악보 전체(검색어·작곡가·시대·조성으로 좁힌 범위)를 기준으로 비교하므로, 기록이 없는 악보도 빠지지 않는다(D2).
- 같은 곡 연결 한 건은 한 번만 센다. "곡 사용 건수"와 "그 악보를 쓴 미사 수"를 둘 다 돌려준다.
- 정렬(제목·작곡가·시대·횟수·조성 C→B·최근 연주일·저장일)은 **전체 결과를 DB에서 정렬한 뒤** 페이지를 나눈다. 동점이면 악보 ID로 고정.
- 돌려주는 값: 악보 ID, 표시 제목, 작곡가 표시, 시대(잠정 여부), 조성, 파일 수·첫 페이지 파일, 조건 안 횟수·전체 횟수·장소 횟수, 마지막 연주일, 전체 건수.

**`search_history(조건)`** — `Performance History` 대상. 같은 조건으로 연주한 곡 한 줄씩(날짜 · Music Part · 장소 · 악보), 최신순/오래된 순.

**인덱스 (적용 전 실제 쿼리 계획으로 확인 후 필요한 것만):** `mass_events(user_id, local_date)`는 이미 있음. 후보: `mass_events(user_id, venue_id)`, `mass_events(user_id, season_code, local_date)`, `owned_scores(user_id, composer_id)`, `owned_scores(user_id, key_tonic, key_mode)`, `composer_aliases(normalized_alias)`. 글자 부분 검색 인덱스(`pg_trgm`)는 확장 기능이 켜져 있는지 확인 후 결정(5장 조회). → 조회 결과 `pg_trgm`·`unaccent`가 꺼져 있다. 지금 악보 수가 적으므로 이번에는 확장 기능을 켜지 않고 일반 글자 비교(`like`)로 검색한다. 악보가 많아지면 그때 따로 승인받아 켠다. 악센트 무시 검색은 작곡가 별칭의 검색용 문자열(`composer_aliases.search_key`)로 처리한다.

**기존 트리거 보완:** `owned_scores`의 수정 시각 트리거는 지금 제목·작곡가 이름이 바뀔 때만 움직인다. 새 칸(작곡가 연결·조성·시대·작곡 연도·메모)이 바뀔 때도 수정 시각이 갱신되도록 같은 함수를 고친다(`created_at` 보호는 그대로).

### 2.9 (선택) 페이지 보존 — SCAN-012

## 3. 화면 계획 (승인 ③에서 실제 화면으로 확인)

모든 화면은 `docs/design-system.md`를 따른다: Pretendard, 48px 버튼·입력, 24px 칩, 카드 radius 12px, 음악 행 최소 48px와 고정 열, 날짜는 한국어, 전례 명칭은 영어, 음악 항목은 라틴어, 작품·작곡가는 원어, 버튼·안내는 영어.

### 3.1 Search 화면 (`#/search`)

- Search 탭과 Home의 `Search` 카드가 이 화면을 연다. 새 탭은 만들지 않는다.
- 위에서부터: 제목 `Search` → 대상 선택 `Scores` / `History` → 검색어 입력(48px) → 필터 칩 줄 → 결과 머리(건수, 횟수 기준 예: `Within Filters`, `Sort`, 보기 `Index` / `Notes` / `Preview`) → 결과.
- 필터 8개(Season & Observance, Date, Composer, Period, Performances, Key, Location, Music Parts)는 칩으로 보이고, 누르면 모바일은 아래에서 올라오는 패널, PC는 칩 아래 작은 패널로 연다. 적용된 조건은 칩에 값이 보이고 `×`로 바로 뺀다.
- **조건 즉시 변경(4.13.9.1):** 필터 하나를 바꿔도 다른 조건·정렬·보기는 그대로다. 조건은 주소(`#/search?...`)에도 담아 뒤로 가기·새로고침 후에도 유지한다.
- 필터 순서와 표시 여부는 사용자가 바꿀 수 있고 `saved_views`에 저장한다(C6). Music Parts 필터의 기본 표시 항목은 C3의 8개, 나머지는 `+ More`로 추가.
- **Index:** 한 줄에 제목(원어), 작곡가 약칭, 조성, 시대, 횟수. 48px 안팎, 열 시작 위치 고정.
- **Notes:** 같은 결과에 악보 메모·연주 메모를 출처와 함께 작게 표시.
- **Preview:** 첫 페이지 미리보기와 `Open Score`. 이미지 악보는 1쪽 이미지를 짧은 서명 URL로, PDF는 화면에 보일 때만 1쪽을 작게 그린다. 썸네일 파일을 따로 저장하지 않으므로 Storage 변경이 없다. 악보가 없으면 가짜 미리보기 없이 `No score available`.
- 결과의 다음 행동: `Open Score`(기존 뷰어), `Add to Missa`(재업로드 없이 연결), `View History`(그 악보의 연주 이력).
- `History` 대상: 한 줄에 `날짜 · Music Part · 장소 · 악보`, 작은 글씨로 촘촘하게.
- 결과가 많으면 `Load more`로 DB에서 다음 페이지를 가져온다.

### 3.2 Missa — 안 친 곡 표시 (D1)

- **지난 미사**(오늘 이전, 취소 아님)의 음악 행 메뉴(⋯)에 `Mark as not played` / `Mark as played`를 추가한다. 미래·오늘 미사에는 보이지 않는다.
- 표시한 곡은 작품 칸에 작은 `Not played` 글자를 붙인다. 새 열을 만들지 않아 번호·역할·작품·메뉴 열 정렬이 그대로다.
- 지난 미사에서 연결 해제를 누르면 "이 곡은 연주 이력에서도 빠집니다. 연주하지 않은 곡이면 `Mark as not played`를 쓰세요."라고 먼저 알린다.
- 지난 미사를 삭제할 때는 "이 Missa의 연주 이력 N곡이 함께 지워집니다."라고 알리고 확인을 받는다(8장 37번). 반복 미사 삭제 목록도 같은 기준을 쓴다.

### 3.3 내 장소 목록 (D3)

- 위치: `Music Parts` 화면(`#/layouts`) 안에 `Places` 구역을 추가한다. 장소마다 이름과 연결할 Music Parts 구성(선택 상자)을 한 줄로 보여 준다. 새 탭은 만들지 않는다.
- Missa 만들기·고치기의 `Where`: 내 장소 목록에서 고르거나 새 이름을 입력한다. 장소를 고르면 연결된 Music Parts 구성이 자동으로 선택되고, 그 미사에서는 바꿀 수 있다. 새 이름을 입력해 저장하면 장소 목록에 새 장소가 생기고, 그때 고른 Music Parts 구성이 그 장소에 연결된다.
- 반복 미사 설정도 같은 방식.

### 3.4 Score Library와 악보 검색 통합 (C7)

- `#/library`(Score Library)는 **내 악보 보관함**으로 남긴다: 업로드, 페이지 편집, Details, Edit, Delete. 탭 이름과 주소는 그대로.
- 별도의 "악보 검색" 페이지는 만들지 않는다. Library 위쪽에 `Search scores` 링크를 두어 `Scores` 대상으로 Search 화면을 연다.
- **Edit:** 작곡가(사전에서 고르거나 글자로), 조성(표준값 + 원래 표기), 작곡 연도, 시대, 악보 메모 칸을 추가한다. 제목·작곡가를 몰라도 저장할 수 있는 지금 규칙은 그대로.
- **Details (SCORE-013·014):** 최초 저장일시(이미 있음) 아래에 실제 연주 횟수와 연주 이력을 넣는다. 이력은 첫 연주일부터 날짜순 `날짜 · Music Part · 성당`, File details 기준(11~12px, 행 간격 1~2px, 열 시작 맞춤)으로 작고 촘촘하게. 지금의 `Linked Missae`(연결 목록, 미래 포함)는 이름을 구별해서 남긴다.

### 3.5 이번 범위 밖

- Performance Mode(4.11, Missa 전체를 순서대로 넘기는 화면)는 별도 작업이다. 검색의 `Open Score`는 이미 있는 뷰어(키보드·페달 넘김 포함)를 쓰고, Performance Mode가 만들어지면 뷰어에 진입 버튼을 붙인다.
- 저장 후 페이지 재촬영·교체 화면(SCAN-012)은 검색 다음 작업.

### 3.6 확인 방법

- 모바일 375·390·430px, 태블릿 768px, PC 1440px에서 정렬·스크롤·버튼·포커스를 확인한다.
- 터치와 키보드(Tab 이동, Enter·Space 선택, Esc로 패널 닫기)로 모든 필터·정렬·보기 전환을 확인한다.

## 5. 승인 ①에서 확인받을 것 — 완료(2026-10-22)

결과: 계획 승인, 읽기 전용 조회 허락, a = 정확히 같은 이름끼리 옮기기, b = 잠정 시대 포함, c = 페이지 보존 함께 넣기.

### 5.1 정해야 할 것

- **a. 기존 장소 이름 옮기기:** 이름이 정확히 같은 것끼리 장소 하나로 만들어 기존 미사에 연결할지(추천), 장소 목록을 비워 두고 사용자가 새로 만들지.
- **b. 잠정 시대:** 작곡가 생몰년에서 나온 잠정 시대를 시대 검색에 포함하고 결과에 "잠정"으로 표시할지(추천), 사용자가 고르거나 작곡 연도가 있는 악보만 검색할지.
- **c. 페이지 보존(2.9):** 이번 DB 작업에 함께 넣을지(추천), 검색 뒤에 따로 할지.

### 5.2 운영 DB 읽기 전용 조회 (값을 바꾸지 않음)

Supabase 연결 도구로 `select`만 실행한다. **이름·제목·이메일·메모 같은 내용은 읽지 않고 개수만 센다.**

1. **구조 확인 (사용자 자료 없음):** 적용된 마이그레이션 목록이 저장소와 같은지, 켜져 있는 확장 기능(`pg_trgm`, `unaccent`), 공개 테이블의 RLS 정책·인덱스·칸 목록, Postgres 버전(보안 뷰 지원 확인).
2. **개수만:** 테이블별 행 수(`owned_scores`, `score_files`, `mass_events`, `mass_music_slots`, `mass_music_entries`, `performance_confirmations`, `user_mass_layouts`, `mass_series`, `works`, `liturgical_observances`), 자료가 있는 사용자 수, 미사의 지난·오늘 이후·취소 개수, 지난 미사에 연결된 곡 수(D1 적용 시 바로 연주로 계산될 수), 장소 이름이 있는 미사 수와 사용자별 서로 다른 장소 이름 수, 공백·대소문자만 다른 장소 이름 쌍의 수, 작곡가 이름이 적힌 악보 수와 서로 다른 작곡가 이름 수, 전례일 자료의 연도별 개수와 첫 날짜·마지막 날짜.

조회 결과는 개수만 보고하고, 마이그레이션 초안에 반영해 승인 ②에서 보여 드린다.

### 5.3 조회 결과 (2026-10-22, 개수와 구조만)

| 항목 | 결과 | 초안에 반영한 것 |

### 6.2 내 컴퓨터에서 미리 시험한 결과 (운영 DB와 무관)

임시 폴더에 메모리 속 Postgres(PGlite, Postgres 18.6)를 띄우고, 저장소의 기존 마이그레이션(Storage 제외) → 예전 방식의 장소 이름이 있는 시험 미사 → 새 초안 4개 순서로 적용했다. Supabase 로그인 역할(`authenticated`)과 `auth.uid()`를 흉내 내어 시험 사용자 A·B로 확인했다. **56개 검사 모두 통과.**

- **적용·옮기기:** 4개 파일이 오류 없이 적용됨. 앞뒤 공백·대소문자만 다른 장소 이름은 한 장소로, 가운데 띄어쓰기가 다른 이름은 다른 장소로 만들어짐. `venue_name` 값은 그대로.
- **D1 연주 판정:** 취소된 미사, 오늘 미사, 미래 미사, `Not played` 곡은 연주에서 빠지고, 표시를 풀면 다시 셈.
- **D2 같은 기록 판정과 횟수:** `Lent + Postludium + 1회`에 사순 시기 Praeludium + 연중 Postludium으로 친 곡이 섞이지 않음. 2회 이상, 0회(기록 없는 악보 포함), "전체 2회 이상 AND 특정 장소 0회", 연도·월·연도 범위, 장소 + Music Part 조합 확인.
- **악보 조건:** 제목 검색(`%`, `_` 글자 안전 처리), 작곡가 이름·사전·별칭 앞글자, 시대(사용자 선택 > 작곡 연도 > 작곡가 잠정 시대, 1900년은 Romantic·1901년은 Modern, 잠정 제외 옵션), 조성, 조성 정렬 C → D → B♭ → 미입력, 페이지 나누기와 전체 건수.
- **권한:** B는 A의 악보·연주·장소·개인 작곡가를 볼 수 없고, A는 B의 곡에 `Not played`를 표시하거나 B 이름으로 장소를 만들 수 없음. 사용자는 검증된 작곡가를 만들거나 운영자 자료를 고칠 수 없음.
- **보호:** 최초 저장일시는 바꿀 수 없고, 조성을 바꾸면 수정 시각이 갱신됨. 뺀 페이지는 행이 남되 파일 수·미리보기에서 빠지고, 저장 경로는 바꿀 수 없음. 장소를 지우면 미사는 남고 장소 연결만 비워짐.

## 7. 화면 작업 결과와 승인 ③에서 확인받을 것

### 7.1 만든 화면 (브랜치 `advanced-search`, 아직 커밋 전)

- **Missa:** 지난 미사의 곡 메뉴에 `Mark as not played` / `Mark as played`와 곡별 연주 메모. 안 친 곡에는 `Not played` 표시. 지난 미사를 지우거나 곡 연결을 풀면 연주 기록도 함께 사라진다고 경고한다(연주한 곡 수 표시). 반복 미사를 지울 때 연주 기록이 있는 날짜는 따로 묶어 보여 준다.
- **Places (Music Parts 화면):** 장소 추가·이름 바꾸기·삭제, 장소마다 Music Parts 구성 하나. 같은 이름(앞뒤 공백·대소문자 무시)은 다시 만들 수 없다. 이름을 바꾸면 그 장소에 연결된 미사의 장소 이름도 함께 바뀐다. Missa를 만들거나 고칠 때 장소를 고르면 그 구성이 자동으로 선택되고, 그 Missa에서만 바꿀 수 있다.
- **Library:** Edit에 조성(으뜸음·장단조 + 악보에 적힌 표기. 표기를 읽어 조성을 제안), 작곡 연도(800~2100, 대략 표시), 시대(기본 Automatic), 악보 메모. Details에 조성·연도·시대·메모와 연주 이력(날짜·Music Part·장소·메모). 위쪽에 `Search scores` 링크.
- **Search (`#/search`):** `Scores` / `History` 대상, 검색어, 필터 칩 8개(모바일은 아래에서 올라오는 창), 연주 횟수 조건과 두 번째 조건(전체 기간 / 장소별), 정렬, `Index` / `Notes` / `Preview` 보기, `Load more`, 필터 표시·순서 저장(`saved_views`), 결과 메뉴의 `Open Score` · `Add to Missa` · `View History`. 조건은 주소(`#/search?...`)에 남아 새로고침해도 유지된다.
