## 0. Cursor에서 이 문서를 사용할 때 지켜야 할 원칙

1. **이 문서는 `무엇을 만들 것인가`를 정의한 요구사항이다.** 코드, DB, API의 현재 구현 상태나 사용 기술을 단정하지 않는다.
2. 기존 회원가입·로그인, Supabase Auth의 `auth.users`, 사용자 UID, 로그인 리디렉션 및 세션 처리를 **사전 승인 없이 변경·삭제·재설정하지 않는다**.
3. 운영 데이터베이스의 테이블 생성·삭제·마이그레이션, 기존 파일 대체, 스토리지 정리 등 위험한 작업을 **사용자의 명시적 승인 없이 실행하지 않는다**. 백업 상태 및 영향 범위를 먼저 확인한다.
4. 구현 전 실제 프로젝트 파일·환경변수의 **키 이름만** 확인하고, 비밀값은 보고서·코드·로그에 노출하지 않는다. 실제 코드와 PRD가 다르면 차이점을 보고한다.
5. 요구사항의 우선순위 `P0(최초 버전의 필수 기능)`, `P1(다음 단계 또는 병행 가능)`, `P2(향후 확장)`를 구별한다. `[미확정]`은 사용자 결정이나 실제 확인이 필요한 사항이다.
6. 새 기능을 구현하기 전 관련 요구사항 ID, 데이터 영향, UI 흐름, 테스트 방법을 제시하고 승인을 구한다. **PRD를 읽은 것만으로 코드 수정을 시작하지 않는다.**
7. 문서 언어는 한국어를 기본으로 하되, 파일명·필드명·기술명·요구사항 ID는 일관된 영어 식별자를 사용한다.

### 요구사항의 우선순위를 읽는 방법

- `필수` = 반드시 구현하고 실제 작동을 확인할 요구사항.
- `권장` = 가능한 한 구현하되 방법·시기 조정 가능.
- `선택` = 나중에 추가할 수 있는 기능.
- `[미확정]` = 설계 전에 확인해야 하며, 임의로 확정하지 말 것.
- **공통 기준 데이터** / **개인 데이터** / **데이터 간 연결 기록** 를 구분한다.

## 1. 서비스 비전과 주요 사용자

### 1.1 제품 비전

ONE ARCHIVE는 가톨릭 오르가니스트, 미사 반주를 담당하는 음악가, 성가대(합창단) 지휘자 및 음악가를 위한 전문적인 전례음악 관리 플랫폼이다.

**전례력 확인 → 성가 선곡 → 미사 준비 → 악보 관리 → 연습 → 실제 연주 → 기록 보존 → 재검색·재사용**을 하나의 작업 흐름으로 연결한다. 단순 파일 저장소가 아닌 **음악가의 전문성과 음악적 경험이 축적되는 작업 공간**을 지향한다.

- **영어 슬로건:** *Prepare. Practice. Perform. It stays with you.*
- **한국어 문구:** 준비하고, 연습하고, 연주하는 그 모든 과정이 당신의 기록으로 남습니다.

### 1.2 주요 사용자

- 가톨릭 오르가니스트 및 미사 반주 담당 음악가
- 성가대(합창단) 지휘자
- 가톨릭 전례음악가 및 음악 담당자
- 전례음악 연구자·학습자
- 미사 반주를 처음 시작하거나 경험이 적은 아마추어 사용자

**[추후 결정 — 용어]** ‘오르가니스트’와 ‘미사 반주자’의 사용자 호칭은 한국에서의 전문성·인상을 고려하여 추후 확정한다. 지금의 표현은 대상 범위 설명용이다.

### 1.3 제품 원칙

1. **정확성:** 전례·음악학적 데이터의 출처, 검증 상태, 불확실성을 기록한다.
2. **전문가의 자율성:** 숙련자에게 불필요한 안내를 강제하지 않는다.
3. **개인 맞춤 구성:** 사용자는 화면에 표시할 정보와 순서를 제어한다.
4. **기록 보존과 재사용:** 미사·선곡·악보·연주 기록은 검색 가능하고 재사용 가능해야 한다.
5. **실제 연주의 안정성:** 실제 미사 중 빠르고 안정적인 악보 이동과 오프라인 사용을 우선한다.
6. **저작권·개인정보 보호:** 본문·악보 저작권과 사용자별 접근 권한을 보호한다.
7. **검색 우선:** **다중 조건 교집합(AND) 검색, 전례 역할, 개인 연주 횟수**는 최우선 핵심 역량이다.
8. **파일 중복 저장 없이 연결:** 한 번 저장한 악보는 파일 복제 없이 여러 일정·템플릿에 재연결한다.
9. **원본을 훼손하지 않는 편집:** 페이지 교체·악보 수정 시 다른 연결과 기록을 손상시키지 않는다.
10. **정교한 내부 구조와 간결한 화면:** 백엔드에는 정확하고 명확한 구조·제약·권한·검색 로직을 유지하면서, 기본 UI는 정보를 최소한으로 노출한다.
11. **필요할 때만 상세정보 표시:** 목록은 한 줄 요약 중심으로 정돈하고, 클릭·터치·키보드 조작으로 상세 정보를 펼친다.
12. **절제된 현대적 디자인:** 넉넉한 여백, 과장 없는 타이포그래피, 세련되고 현대적이되 취향이 과하게 드러나지 않는 객관적·중립적 디자인을 추구한다.
13. **나중에도 바꿀 수 있는 디자인:** 초기 디자인은 일관된 기본값을 제공하며, 향후 사용자별 배경색·폰트·첫 화면 대표 이미지 변경을 지원할 수 있도록 데이터와 화면을 분리한다.
14. **서로 다른 세 화면:** `내 레퍼토리(My Repertoire)`(작품 중심) · `악보 검색`(본인 소유 악보 파일 중심) · `날짜별 미사 상세`(그 날짜의 미사와 악보 중심)은 독립적인 화면이되 서로 자연스럽게 이동·연결된다.
15. **사용자가 조절하는 정렬:** 정렬 메뉴의 항목·순서·기본 정렬은 개인화한다. 정렬(Sort), 필터(Filter), 그룹화(Group)는 의미를 구별한다.
16. **악기·사진·음원의 출처 관리:** 역사적 오르간 사진·오르간 사양·음원, 미사 후 녹음·유튜브 링크는 출처·권리·확실성을 검증한 후 작품·장소·미사에 연결한다.

## 3. 사용자가 실제로 서비스를 이용하는 순서

### FLOW-001: 선곡을 위한 검색 → 악보 연결 → 미사 준비 [P0]

1. 사용자가 작품명/작곡가 또는 필터를 사용해 검색한다.
2. `전례 시기`, `전례 역할`, `조성`, `연주 횟수` 등을 동시에 선택한다.
3. 시스템은 **모든 조건을 만족하는 결과만** 표시하고, 횟수의 종류와 집계 범위를 밝힌다.
4. 사용자는 작품의 음악학 정보와 자신이 보유한 악보를 확인한다.
5. 이미 저장한 악보를 재업로드하지 않고 미사 일정 또는 템플릿의 특정 순서에 연결한다.
6. 미사 목차에서 곡을 선택하면 해당 악보가 열리고 연주 모드로 진입할 수 있다.

### FLOW-002: 미사 준비 → 실제 연주 → 아카이브 [P0]

1. 날짜별 미사를 생성한다. 같은 날짜에 다른 시간/장소의 미사를 추가로 만들 수 있다.
2. 템플릿을 적용하거나 곡을 직접 추가하고 전례 역할·순서·악보를 지정한다.
3. 목차와 연결된 악보를 검토한다. 오프라인 기능이 준비된 경우 사전 다운로드를 확인한다.
4. 미사 후 실제 연주 여부를 기록한다.
5. 확인된 연주만 확정 연주 횟수에 반영하여 이후 검색에 재사용한다.

### FLOW-003: 악보 촬영 → 보정 → PDF → 특정 페이지 재촬영 [P1]

1. 악보를 여러 장 촬영한다.
2. 밝기/기울기/원근 등을 보정하고 페이지 순서대로 PDF를 저장한다.
3. 10쪽 중 5쪽만 다시 촬영하면 5쪽을 교체하고 나머지 페이지를 유지한다.
4. 사용자는 수정 결과를 미리 보고 저장하며 원본 보관·삭제 여부를 선택한다.
5. 이미 연결된 미사/템플릿이 어느 악보 버전을 보는지 확인할 수 있다.

### FLOW-004: 캘린더 날짜 → 미사 상세 → 연습/미사 모드 [P0]

1. 캘린더에서 과거·오늘·미래의 날짜를 선택한다. 날짜 헤더는 `2026년 12월 25일(금요일)`처럼 **크고 명확하게** 표시한다.
2. 그날의 전례력·전례색을 확인하고 같은 날짜의 여러 미사를 별도 카드/목록으로 선택한다.
3. 선택된 미사의 곡 목차(곡명·작곡가·역할·악보 상태)를 보며 `+ 곡 추가` 또는 `기존 악보 검색`으로 연결한다.
4. 목차 또는 악보에서 연습 모드와 미사 모드로 직접 진입한다. 악보를 마지막 페이지까지 보고 다음 곡으로 넘어간다.
5. 날짜가 이미 지났더라도 곡·악보·메모를 소급 입력할 수 있다. 실제 연주 확인은 별도 명시적인 동작으로 처리한다.
6. 미사 후에는 전체 미사 또는 개별 곡에 음원, 영상 링크, 메모를 연결한다(미디어는 P1).

### FLOW-005: 악보 검색 → 기존 파일 재사용 [P0]

1. 좌측 메뉴에서 **`악보 검색`** 을 독립 화면으로 연다. 범용 작품 검색·My Repertoire와는 별도의 탐색 시작점이다.
2. 자신의 PDF/이미지 악보를 **파일명·작품명·작곡가·작품번호·판본·파일 형식·보유 상태** 등으로 찾는다.
3. 결과에서 원본 파일/현재 버전을 미리 열어 보고, 선택한 미사의 특정 곡 목차 또는 템플릿으로 연결한다.
4. 파일 바이너리를 복제하지 않고 `owned_score_id`를 재사용한다. 하나의 연결을 해제해도 원본과 다른 일정의 연결은 유지한다.
5. **PDF 안의 악보 음표를 자동 검색하는 기능은 초기 범위에 포함하지 않는다.** 파일 내부 문자 검색은 텍스트 추출/인덱싱이 가능한 경우에만 별도로 검토한다.

### FLOW-006: 레퍼토리 정렬 및 표시 메뉴 편집 [P0]

1. 사용자는 `내 레퍼토리`에서 기본 한 줄 목록을 본다(곡명+작품번호, 작곡가/생몰년/국적을 최대 두 줄로 압축).
2. 정렬 메뉴를 열어 알파벳순·가나다순·전례 시기별·전례 역할별·음악사 시대별·저장한 순서·연주 횟수순 등을 선택한다.
3. `표시할 정렬 항목 편집`에서 **자신이 사용할 정렬 항목만 표시/숨김**, 항목 순서 재배열, 기본값을 설정한다.
4. 전례 시기 그룹은 `대림→성탄→사순→부활→연중`, 시대 그룹은 `르네상스→바로크→고전→낭만→20세기→현대`의 **제품 지정 순서**를 따른다. 그룹에 속하지 않는 값은 `미분류`로 처리한다.
5. `전례 역할`은 해당 작품의 **개인 미사 사용 기록** 또는 검증된 작품 활용 태그 중 어디서 도출했는지 구별한다. 한 작품의 여러 역할은 그룹에서 중복 표시 가능하되 **작품·연주 통계 자체는 중복 집계하지 않는다**.

## 4. 기능별 상세 요구사항

### 4.1 전례력 [P0]

- **LIT-001 필수:** 운영자가 검증한 날짜별 가톨릭 전례 정보를 제공한다. 데이터: 날짜, 전례일 명칭, 전례 시기(대림·성탄·연중·사순·부활), 전례색, 복음 환호송 및 고유 구절, 복음 참조, 출처·검증 상태. 제1·제2독서 참조는 4.2에서 다룬다.
- **LIT-002 필수:** 날짜는 **`2026년 10월 25일(일요일)`**처럼 `YYYY년 M월 D일(요일)` 형식으로 명시한다.
- **LIT-003 필수:** 전례일 표시 예시: `연중 제30주일 (녹) ●`. 전례색 약어 `(녹)`, `(백)`, `(자)`, `(홍)`, `(분홍)` 등을 명칭 옆에 실제 색과 함께 표시한다. 별도 전례색 설명란은 기본 화면에서 제외한다.
- **LIT-004 필수:** 전례일 명칭과 색 표시는 숨길 수 없으며, 색상은 단순히 전례 시기에서 추론하지 않고 검증한 해당 날짜 자료를 따른다. 예외 색상 확장이 가능해야 한다.
- **LIT-005 권장:** 별도의 전례적 주제·선곡 해설은 현재 필수 정보가 아니며, 검증된 공식 규범과 운영자 의견을 구별할 수 있는 방식으로만 향후 검토한다.

### 4.2 독서·복음 및 저작권 [P0 기본 제공 / P1 본문 표시]

- **GOS-001 필수:** 제1독서·제2독서(있는 날)·복음의 성경 참조와 복음 환호송의 공식 참조를 표시할 수 있다.
- **GOS-002 필수:** 복음 본문 앱 내 열람을 목표로 하지만 **이용 허락 전에는 무단으로 복제·저장·재배포하지 않는다**. 우선 적법한 공식 외부 출처로 연결한다.
- **GOS-003 필수:** 본문 제공 권한이 확보되면 권리자, 번역본, 출처, 허가 범위, 표시 의무, 저장·캐싱·배포 조건을 기록하고 그 범위 안에서 앱 내 표시한다.
- **GOS-004 필수:** 웹에서 공개된 문헌이라고 해서 스크래핑·임베딩·복제 권한이 자동으로 주어지는 것은 아니므로 사용 조건을 검토한다. 복음 환호송의 문구 권한도 별도 확인한다.

### 4.3 운영자 전례력 관리 [P0 기본 기능 / P1 관리자 화면 편집]

- **ADM-001 필수:** 운영자는 공통 전례 데이터를 생성·수정·검증·공개하고 출처·검증 상태·수정 이력을 관리한다.
- **ADM-002 필수:** 일반 사용자는 운영자 공통 원본을 편집할 수 없다.
- **ADM-003 권장:** 관리자용 입력 화면의 필드 표시, 순서, 그룹, 안내 문구를 운영자가 변경할 수 있다. 데이터와 UI 구성은 분리한다.
- **ADM-004 선택:** 운영자가 사용자 정의 필드를 추가하는 기능은 추후 지원한다.

### 4.4 지역별·특별 미사 [P0]

- **SPC-001 필수:** 지역별 전례·성당 고유 전례·장례·혼인 등의 특별 미사/예식 설정을 **개별 미사 일정**에 연결한다.
- **SPC-002 필수:** 개인의 특별 미사 설정은 공통 전례력 데이터를 덮어쓰지 않는다.
- **SPC-003 필수:** 실제 전례일·독서 선택의 허용 범위는 해당 전례 규정에 따라 별도 확인한다. 임의 선택을 공식 자료로 표시하지 않는다.

### 4.5 개인별 전례력 화면 [P0]

- **VIEW-001 필수:** 전례 시기, 제1·제2독서, 복음 환호송, 복음 참조, 복음 본문 열기 등에서 사용자가 볼 항목과 순서를 설정·저장한다.
- **VIEW-002 필수:** 운영자 지정 기본 보기 + `최소`, `기본`, `상세`, `사용자 지정` 보기를 지원한다. 여러 저장된 화면 구성 간 전환도 가능해야 한다.
- **VIEW-003 필수:** 전례일 명칭과 전례색을 숨길 수 없고, 숨긴 항목의 원본 데이터는 삭제되지 않는다.
- **VIEW-004 필수:** 설정은 로그인 계정별로 보관되어 재로그인 후에도 유지된다.

### 4.6 미사 일정·곡 목차 [P0]

- **MASS-001 필수:** 미사 일정 CRUD 및 **동일 날짜 복수 미사**를 지원한다. 일정별 날짜·시간·성당/장소·전례일·특별 미사 설정·곡 순서·악보·개인 메모·템플릿을 별도 관리한다.
- **MASS-002 필수:** 일정 또는 템플릿을 선택하면 **곡 순서가 반영된 목차**가 보이고, 목차 항목을 누르면 연결 악보가 열린다.
- **MASS-003 필수:** 악보 첫 페이지에서 마지막 페이지까지 이동하고, 다음 페이지·다음 곡으로 연결된다. 악보 미등록 항목은 오류 대신 안내를 표시한다.
- **MASS-004 필수:** 목차와 악보 화면에서 연주 모드로 바로 전환한다.
- **MASS-005 필수:** 한 미사의 변경은 동일 날짜의 다른 미사 내용을 임의로 변경하지 않는다.
- **MASS-006 필수:** 미래 미사 선행 입력뿐 아니라 지난 날짜의 미사와 해당 음악/악보를 언제든 소급 입력·수정할 수 있다. 날짜가 과거라는 사실로 `완료`나 `연주 완료`를 자동 판정하지 않는다.
- 🔵 **`[보완·v0.4 이후]` MASS-008 필수 [P0]:** 관리자 제공 **기준 미사 순서**와 사용자가 선택하는 **음악 항목·악보·명칭**은 별도 구조로 관리한다. 음악 가능 위치 17개는 부록 A.
- 🔵 **`[보완·v0.4 이후]` MASS-009 필수 [P0]:** 미사의 전주·입당·영성체·후주 등 **각 음악 항목에서 즉시 카메라 촬영 또는 파일 업로드, 기존 악보 검색·연결**이 가능하며, 새 악보는 자동으로 내 라이브러리에 등록한다.
- **MASS-007 필수:** 캘린더 날짜 선택 → 큰 날짜 헤더 + 공식 전례일/색상 → 그날 미사 카드 → **곡·작곡가·전례 역할·악보 연결 상태가 보이는 목차** → 곡 선택/연습/미사 모드까지 연결한다. 동일 날짜 복수 미사는 독립 구분한다.
- **MASS-010 권장:** 날짜별 미사 상세 화면에서 `곡 추가`, `저장한 악보 찾기`, `템플릿 가져오기`를 제공한다. 미사 후 녹음·영상 링크는 P1 기능이며 날짜 기록 아래 연결한다.

### 4.7 반복 미사 템플릿 [P0]

### 4.8 음악학적 작품 정보 [P0 핵심 자료]

### 4.9 악보 보관함과 재사용 [P0]

- **SCORE-001 필수:** PDF·JPG·PNG 등 악보를 업로드하여 작품·판본·편집자와 연결한다. 파일은 기본적으로 개인 비공개이고 공유/배포는 저작권 및 접근 권한에 따른다.
- **SCORE-002 필수:** **한 번 저장한 악보를 재업로드 없이** 여러 주일/평일/특별 미사, 다른 날짜의 미사, 복수 템플릿, 연습 목록, 개인 연주 기록에 반복 연결한다.
- **SCORE-003 필수:** 악보 파일 자체의 고유 ID와 미사·템플릿·연습 목록에서 악보를 가리키는 **연결 ID**를 분리한다. 연결별 곡 순서·전례 역할·메모는 독립 저장한다.
- **SCORE-004 필수:** 한 곳의 악보 연결 해제가 다른 연결·원본 파일을 삭제하지 않는다. 악보 자체를 삭제할 때 다른 연결에 대한 영향을 사전 표시하고 확인을 받는다.
- **SCORE-005 필수:** 작품 하나에 여러 판본·개인 악보를 연결할 수 있으며, 검색과 목차에서 자신의 기존 악보를 선택할 수 있다.
- **SCORE-006 권장 / [미확정]:** 악보를 수정했을 때 기존 일정이 최신 버전을 자동 사용하는지, 연결 당시 버전을 유지하는지 **정책을 확정**하고, 사용자에게 명시한다. 결정 없이 운영 데이터를 변경하지 않는다.
- **SCORE-007 필수:** `악보 검색`은 **별도 메뉴와 별도 페이지**를 가진다. 기존 업로드 악보를 파일명·작품명·작곡가·작품번호·판본·형식·업로드일·연결 여부 등으로 검색하고 즉시 미리보기/연결할 수 있어야 한다.
- **SCORE-008 필수:** `악보 검색` 결과는 로그인한 사용자에게 접근 권한이 있는 실제 악보 파일만 노출하며, 작품 메타데이터만 있는 항목을 **보유 악보인 것처럼 표시하지 않는다**. 저장된 악보는 여러 미사/템플릿에 반복 연결한다.
- **SCORE-009 권장:** PDF 텍스트 인덱싱은 추출 가능한 텍스트에 한하여 추가 가능하나, 악보 사진의 음표·오선 검색은 OMR 기술이 필요할 수 있으므로 별도 후속 범위로 다룬다.
- 🔵 **`[보완·v0.4 이후]` SCORE-010 필수 [P0]:** 카메라 촬영 **또는** 기존 PDF/JPG/PNG 업로드를 허용하며, 추가 위치와 관계없이 한 개의 개인 악보 자산으로 저장·검색·재사용한다. 원본 PDF는 불필요한 재인코딩을 강제하지 않는다.
- 🟢 **`[신규·v0.4 이후]` SCORE-011 필수 [P0]:** 작품 정보가 없어도 먼저 저장하고, 미분류 개인 레퍼토리/악보 검색에서 확인할 수 있다. `work_id` 미연결 상태는 허용하되 가짜 작품/작곡가를 만들지 않는다. 세부 구현은 4.23~4.25.

### 4.10 악보 촬영·보정·PDF 편집 [P1]

- **SCAN-001 필수:** 카메라 이미지의 문서 경계, 원근, 기울기, 회전, 밝기·대비·배경을 보정하고 여러 페이지를 PDF로 결합한다.
- **SCAN-002 필수:** 오선·음표·임시표·덧줄·슬러 등 가는 기호가 사라지지 않도록 최종 결과 미리보기와 수동 조정을 제공한다.
- **SCAN-003 필수:** 저장 후 개별 페이지 추가·삭제·회전·순서 변경·재촬영 **교체**가 가능해야 한다. 예: 10쪽 중 5쪽만 재촬영하여 같은 위치에 끼워 넣고 다른 쪽은 보존한다.

- **SCAN-006 권장:** 비용을 줄이기 위해 이미지의 실사용 품질을 기준으로 압축·흑백/회색조/컬러 선택·경량 미리보기·페이지 단위 처리 방식을 비교한다. DPI·목표 용량·원본 보관기간은 **실제 악보 품질 테스트 후** 결정한다.
- **SCAN-007 선택:** 악보 음표 자체를 분석하는 OMR·OCR은 후속 단계로 둔다.

### 4.12 개인 연주 기록과 연주 횟수 [P0]

- **HIST-001 필수:** 날짜·장소·작품·전례 역할·연결 악보·템플릿·메모로 과거 미사 및 연주 기록을 찾아 재활용한다.
- **HIST-002 필수:** 다음 통계는 별도 개념으로 다룬다.
  - `assigned_count`(배정 횟수): 작품을 미사 일정의 곡 항목에 배정한 건수(계획 포함).
  - `confirmed_performance_count`(확인된 연주 횟수): 실제로 연주했다는 확인이 기록된 건수.
  - `estimated_from_schedule_count`(일정에 근거한 추정 횟수): 과거 일정에 근거한 추정 건수(확정 실적으로 표시 금지).
- **HIST-003 필수:** 취소 또는 계획 상태인 미사의 작품을 **자동으로 확정 연주 횟수로 세지 않는다**. 실제 연주 여부를 확인하는 절차를 제공한다.
- **HIST-004 필수:** 동일 작품이 한 미사에서 여러 번 사용되었다면 `연주 사용 건수`와 `해당 작품을 사용한 미사 수`를 구별하여 집계할 수 있도록 설계한다. 집계 기준은 결과 화면에 명시한다.
- **HIST-005 필수:** 횟수는 **로그인한 사용자의 기록만** 기준으로 계산한다. 공개 작곡가·작품 정보와 사용자별 연주 통계를 혼합하지 않는다.

### 4.13 통합 검색·교집합 검색 [**P0 — 가장 중요한 기능**]

> 단순한 키워드 검색이 아니라 **전례 시기 + 실제 사용된 전례 역할 + 조성 + 개인 연주 횟수** 등의 조건을 동시에 만족하는 작품을 찾는 것이 ONE ARCHIVE의 핵심 가치다. 데이터 구조를 처음부터 이에 맞춰 설계한다.

**검색 대상 및 필터 — SRCH-001 필수**

- 작곡가, 곡명, 작품번호, 원어/영어/한국어 제목 및 번역 제목
- 시대(바로크·고전·낭만·현대 등), 음악적 형식·양식, 조성
- 전례 시기(대림·성탄·연중·사순·부활), 전례일, 날짜/기간
- 전례 역할(전주·후주·영성체 후 묵상 등) **및 해당 작품의 미사 사용 기록**
- 성가 제목·번호, 개인 악보/판본 보유 여부
- 개인 미사 일정 배정 횟수, 확인된 연주 횟수, 추정 횟수
- 개인 미사·템플릿·아카이브의 연관 기록

**다국어·별칭 — SRCH-002 필수**

- 작곡가·작품의 표준 식별자와 별칭(Alias)을 관리한다.
- `Bach / 바흐 / J. S. Bach / Johann Sebastian Bach`가 동일 작곡가를 찾을 수 있어야 한다.
- `d minor / dm / 라단조` 등 조성 동의어를 표준값에 연결한다. 원곡/편곡/판본의 조성 차이를 임의 병합하지 않는다.
- 작품번호 정확 일치를 우선하고, 대소문자·띄어쓰기·가벼운 오탈자를 보완한다. 제목이 같은 서로 다른 작품을 구분한다.

**교집합 검색 규칙 — SRCH-003 필수**

1. 여러 필터는 기본적으로 논리 연산자 **`AND`(모든 조건을 만족)** 로 결합한다.
2. 예시 A: `전례 시기 = 성탄` **AND** `확인된 연주 횟수 ≤ 2회`.
3. 예시 B: `전례 역할 = 영성체 후 묵상` **AND** `조성 = d minor` **AND** `확인된 연주 횟수 ≤ 3회`.
4. 횟수 비교는 **`≤ (이하)`, `≥ (이상)`, `= (정확히)`, `최소~최대 (범위)`**, 그리고 **0회**를 지원한다.
5. 횟수의 **유형**(`배정/확인/추정`)과 **집계 범위**(`전체 기간` / `현재 선택한 시기·역할·기간 조건 내`)는 사용자가 구별해 선택할 수 있어야 한다.
6. 여러 문맥 필터가 사용 기록을 기준으로 적용되면, **동일한 곡 사용 기록 또는 요구된 동일한 맥락**이 조건을 충족해야 한다. 서로 무관한 다른 미사에서의 `성탄` 기록과 `영성체 후 묵상` 기록을 임의로 결합해 허위 결과를 만들지 않는다.
7. **0회 검색 주의:** 전례 시기/역할을 `과거 실제 사용 기록`에서만 찾으면 그 조건에서 미연주 작품은 검색되지 않는다. 향후 `작품의 전례적 활용 태그`와 `나의 과거 사용 기록`을 별도 필터로 제공할지 **[미확정] 결정**한다. 허위 과거 이력을 만들지 않는다.
8. 연주 횟수는 본인 데이터로만 계산한다. 기록이 없는 경우와 권한 때문에 볼 수 없는 기록을 혼동하지 않는다.

**결과와 다음 행동 — SRCH-004 필수**

- 기본 결과: **작품명(작품번호 포함), 작곡가, 자료 유형**. 사용자는 추가 표시 메타데이터와 순서를 설정한다.
- 각 결과에는 검색에 사용한 연주 횟수의 **유형·범위**를 확인할 수 있어야 한다.
- 작품의 음악학 정보 → 보유 악보/판본 → 과거 연주 기록으로 이동한다.
- 검색 결과에서 기존 악보를 **재업로드 없이** 새 미사·템플릿·연습 목록에 연결한다.

**정확성·보안·성능 — SRCH-005 필수**

- 정확한 작품번호와 작품명 일치를 우선하며, 별칭·동의어·철자 변형에 대응한다.
- 공통 메타데이터와 권한 있는 개인 기록을 검색하되, 다른 회원의 비공개 파일·연주 횟수를 표시하지 않는다.
- 대표 검색어 및 예상 결과(검증용 예시 데이터)를 테스트로 유지한다. 특히 `0회/2회/3회 경계`, `≤ ↔ ≥`, `완료/계획/취소`, `복수 미사 동일 날짜`, `같은 작품의 복수 곡 항목`, `서로 다른 기록의 잘못된 결합`을 검증한다.
- PostgreSQL 정규화 테이블, 적절한 인덱스, Full-Text Search, 별칭, 필요시 `pg_trgm` 등을 **기술 후보**로 검토한다. 확정 스택은 실제 저장소 확인 후 결정한다.

**향후 AI 검색 — SRCH-006 선택 [P2]**

- 자연어/의미 검색은 후속 확장이다. **기본 메타데이터 검색·교집합 검색·연주 횟수 검색을 AI 개발보다 먼저** 구현한다. AI 생성 내용과 검증된 학술 사실을 구분한다.

- **SV-003 필수:** 미사 슬롯/템플릿/연습 목록에서 **원본 또는 특정 편집본**을 선택하며, 연습·미사 모드에서 그 편집본에 정해진 페이지만 그 순서대로 넘긴다.
- **SV-004 필수:** 한 악보의 원본 페이지를 수정한 `파일 리비전(Revision)`과, 어떤 페이지를 연주할지 선택한 `연주용 편집본(Performance Version)`은 **서로 다른 개념**으로 저장한다. 편집본은 사용된 원본 리비전을 식별하고, 부모 리비전 삭제 시 기존 연주 기록이 손상되지 않게 한다.
- **SV-005 필수:** 작품 전체 횟수는 동일 작품의 여러 편집본을 합산하되, **한 곡 사용 기록을 편집본 개수만큼 중복 계산하지 않는다**. 버전별 횟수는 별도 조회로 제공한다.
- **SV-006 선택 [P2]:** PDF 페이지 내부의 **마디 단위 시작·종료·생략 구간 지정**은 차후 확장 가능하게 한다. PDF 특정 페이지 선택만으로 실제 마디 중간 생략을 정확히 표현할 수 없음을 명시한다.

## 5. 데이터 소유권과 연결 관계

### 5.1 데이터를 누가 관리하는가

- **운영자 공통 데이터:** 공식 전례력, 검증된 전례 자료, 공통 작곡가 및 작품의 학술 메타데이터.
- **사용자 개인 데이터:** 개인 미사, 미사별 곡 순서/전례 역할/상태, 개인 악보 파일, 파일 보정 원본, 악보 다중 연결, 연주 확인 이력, **미사 녹음·외부 영상 링크**, 개인 메모, **정렬 메뉴 설정·레퍼토리 수동 순서**, 보기 설정 및 개인 특별 미사.
- **추가 공통 자료(관리자 검증):** 역사적 오르간·교회/장소·스톱 구성표·검증된 사진·음원·작품 연결 근거. 개인 오르간 메모와 공개 참조 자료는 분리한다.
- **권한:** Supabase 인증 및 Row Level Security(RLS)를 통한 사용자별 접근 제어. 관리 권한을 일반 회원 권한과 분리한다.

### 5.2 어떤 정보가 서로 연결되는가 (실제 테이블명은 `docs/database.md` 참고)

```text
작곡가(Composer) 1명 → 작품(Work) 여러 개
작품 1개 → 악보 판본 여러 개
작품 1개 → 사용자별 악보 여러 개
사용자 1명 → 미사 일정 여러 개
미사 일정 1개 → 역할·순서가 지정된 음악 항목 여러 개
미사 음악 항목 1개 → 작품 1개와 연결 / 악보는 없을 수도 있음
사용자 1명 → 개인 미사 템플릿 여러 개 → 각 템플릿의 음악 항목
사용자 악보 1개 → 여러 미사·템플릿·연습 목록에 연결 가능
미사 음악 항목 1개 → 연주 확인 기록을 여러 개 연결 가능
사용자 1명 → 개인 화면 구성·정렬 설정·수동 정렬 순서
미사 일정 1개 → 녹음 파일·외부 영상 링크 여러 개
작품 여러 개 ↔ 관련된 역사적 오르간 여러 개 (근거·관계 유형 구분)
오르간 1대 → 사양·사진·음원·사용자 개인 메모
전례력의 한 날짜 → 여러 미사 일정 (미사별 특별 설정 가능)
```

> 관계도는 **개념 설계**다. 현재 Supabase에 위 이름의 테이블이 존재한다는 의미가 아니다. 실제 DB 확인 후 정규화, 연결 모델, 중복 방지, 버전 정책을 결정한다.

### 5.3 기록과 연주 횟수를 계산하는 원칙

- 작품의 **공통 정체성(Work ID)**, 사용자가 보유한 **악보(Score ID)**, 실제 곡 배정/사용 이력(**Music Entry ID**)은 서로 대체할 수 없다.
- 검색 통계는 사용 기록과 상태로부터 계산하거나 검증된 집계값을 사용한다. 숫자만 별도로 수동 입력해 이력을 잃지 않는다.
- 한 미사에서 여러 번 연주한 같은 작품, 여러 미사에 연결된 같은 악보, 같은 작품의 다른 편곡/판본을 명확히 구분한다.
- 삭제·교체·권한 변경이 다른 연결 또는 다른 회원 데이터에 영향을 주지 않도록 설계한다.

**Cursor에 처음 요청할 작업은 기존 프로젝트를 조사하는 것뿐이야.**

3. 특히 **SRCH-003(교집합·횟수 계산)** 과 **SCORE-002~004(악보 재연결)**, **MASS-002~004(목차→악보→연주 모드)** 구현에 필요한 최소 데이터 관계를 제안한다.
   - **UI-001~UI-016, SORT-001~008, DAY-001~006, FIND-001~006:** 업로드된 레퍼런스 화면에 맞는 좁고 조밀한 레퍼토리/넓은 날짜별 미사 상세/독립 악보 검색 화면을 검토한다. 기본 UI를 임의로 복잡하게 확장하지 않는다.
   - **MEDIA-001~007, ORGN-001~004:** 녹음·영상 링크와 역사적 오르간 데이터는 사용자 승인 전 구현이 아닌 확장 설계로 확인한다.

5. 승인 후 `docs/database.md`, `docs/architecture.md`, `docs/api.md`, `docs/progress.md`를 실제 코드와 동기화하면서 기능별로 구현한다. **요구사항은 이 PRD가 기준이지만, 실제 구현 사실은 반드시 코드와 테스트로 입증한다.**

**금지:** PRD를 근거로 인증 설정 변경, `auth.users` 재생성, 운영 데이터 삭제, 비밀키 노출, 백업 확인 없는 파괴적 마이그레이션, 접근 권한 없는 사용자 데이터 열람을 실행하지 않는다.
